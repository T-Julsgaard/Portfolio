# Portfolio 2.0 — ASCII Portrait Site

A single-file, no-build Three.js prototype: an interactive ASCII-art portrait (13,268 glyphs) the visitor can fly through. No framework, no bundler — everything lives in one HTML file.

The portrait data (as of v18) is a direct Grainrad ASCII generator export (172×157 grid, standard charset `.:-=+%#@*`, all-white). The 19 frames in `PROGRESSIVE_FRAMES` (34 → 3,791 glyphs, coarse → fine) drive the "Progressive" load animation; unlike the pre-v18 set (which came from Grainrad itself), they are generated offline by downsampling the embedded `asciiData` onto coarser grids (5 → 64 columns, representative glyph per cell = fine glyph nearest the cell centre, cell z = mean depth) — so a portrait swap requires regenerating them from the new data. Bounds/constants (`centerX/Y`, `spanX/Y`, `midZ`, `farDist`, fog, the journey path and its terrain heightmap) are all derived from the embedded `asciiData`, so swapping the portrait data automatically re-scales the whole scene. Glyph geometry is cached per unique character (`glyphGeo`) and shared across all instances — required at this glyph count — with a dash fallback for symbols the helvetiker font lacks (`∏ ∑ √ ÷ ≠ ≥ ≤ ×`). Since v28 the geometry is a flat `ShapeGeometry` (same font outlines the old extruded TextGeometry used; the 0.02 extrusion was invisible on billboarded unlit glyphs and doubled the triangle count).

**Rendering architecture (v29 — instanced pools).** The 13,268 glyphs are NOT individual meshes anymore (they were through v28, which was the old-hardware bottleneck: 13k draw calls + per-object matrix/cull/sort work every frame). Each unique character owns one `InstancedMesh` (a "pool", 9 for the portrait charset, more created lazily for assembled stop text); a glyph is a lightweight `Glyph` proxy `{position, scale, visible, material:{color,opacity}, geometry, userData}` holding a slot in a pool, so all animation code manipulates proxies exactly like the old Meshes. Assigning `.geometry` (the facets' mid-flight character swap) moves the glyph between pools. `syncPools()` rewrites the instance buffers only on frames where glyph state changed (`glyphsDirty` — every animation path sets it; a missed path shows up as glyphs frozen until the next dirty frame, so set it when adding new animations). **v50**: `syncPools` additionally compares every value before writing (in f32 via `Math.fround` — the proxies hold f64, the arrays f32, so raw compares would never match) and flags `needsUpdate` per attribute per pool only when bytes actually changed — a settled docked stop (where `updateAssembly` marks `glyphsDirty` every frame merely because facets exist) uploads nothing, and e.g. the gallery's button pulse re-sends only the `#` pool's colors instead of all ~1MB of instance data. `glyphsDirty` semantics are unchanged — keep setting it from every animation path; the compare only skips bytes-equal GPU uploads, so it cannot cause the frozen-glyph failure mode. Billboarding is free: instance matrices carry translation+uniform-scale only and the camera quaternion (`BB_UNIFORM`/`uBB`, one shared uniform) rotates glyph vertices in the vertex shader via `GLYPH_MAT.onBeforeCompile` (which also adds the per-instance `instanceOpacity` attribute; per-instance color rides the built-in `instanceColor`). All pools share the single `GLYPH_MAT`; pool geometry is a *clone* of the `glyphGeo` cache entry because the generator preview still uses the cache geometry on plain Meshes. Photo tiles get `renderOrder=-1` (draw before the pools) to preserve the old per-mesh depth-sort behavior during the develop. A `renderDirty` flag forces repaints for non-camera changes (dev sliders, invert/raw, generator); a fully settled overview skips rendering identical frames. Known acceptable deviation: overlapping *semi-transparent* glyphs blend in pool/slot order rather than exact depth order, visible only mid-animation on black — the settled scene is unaffected. The generator preview (`genPreviewMeshes`) still uses plain Meshes.

**Load animations** (selectable in dev tools, replayable): `progressive-soft` (default, v22 — same coarse→fine ramp, but instead of the final hard cut the 13k real glyphs dissolve in individually over ~2.2 s, staggered with a slight peaks-first bias, while the held last frame melts away underneath; the camera push-in spans the whole run so the finish has no jump), `progressive` (the original ramp — resolves through the 19 frames, then snaps to the full portrait; the snap is a ~3.5× density jump, which is why the soft variant exists) and `surface` (the ember/parallax reveal: glyphs surface out of the relief, igniting hot then cooling, while the camera arcs from a close 3/4 angle out to the overview). `beginIntro(mode)` is the single entry point.

**Music bar** (v30; playlist grown to 78 tracks in v32): a minimal fixed pill in the top-right corner (`#music`, styled like the journey buttons — 10px uppercase mono, hairline border, blur backdrop) streaming the playlist through a hidden 2×2 YouTube IFrame player (`#yt-audio-wrap`). It's a self-contained plain `<script>` IIFE just before the main module — playlist lives in its `TRACKS` array (id + "Artist — Title" label; adding a song is genuinely plug-and-play — append one entry, the bar auto-skips any that turn out embed-disabled). New batches are parsed offline from a links markdown and oEmbed-checked for dead/private IDs before insertion. UI: 4-bar CSS equalizer (animates when `.playing`, staggered opacity pulse while `.wait`ing for the stream), marquee title (ping-pong `--mq`/`--mqd`, only when the label overflows 172px; the title is a link to the video on YouTube), prev (restarts after 3 s, classic behavior), play/pause, next, and volume (slider expands on hover; scrolling anywhere on the bar nudges volume and flashes the slider via `.volshow` — `stopPropagation` keeps it from charging the journey departure; window pointer handlers already ignore non-canvas targets). The IFrame API script preloads at startup but the embed is only created when playback first starts, so autoplay-with-sound rides the gesture + `allow="autoplay"` delegation; track end auto-advances, embed-blocked videos are skipped (label "stream unavailable — press play to retry" after a full failed cycle; play resets the streak), and volume persists in `localStorage` (`pf_music_vol`; **default 25%** when unset). **Autostart** (v33, reworked v35, repaired v45): browsers block *audible* autoplay without a user gesture but always allow *muted* autoplay, so v35 begins playback **muted the instant the page loads** (`setTimeout(autostart,0)` — the equalizer runs, the clock ticks) and **unmutes on the visitor's first interaction**. `effMute() = muted || !engaged` gates every mute/unmute (onReady + `applyVolume`); the first-interaction path (`engage()`) flips `engaged` and unmutes+plays. `engage` is armed as one-shot capture listeners on `mousemove`/`pointerdown`/`keydown`/`wheel`/`touchstart` — `mousemove` is included so on this cursor-driven page the music usually goes audible the moment the mouse moves; the discrete gestures are the reliable fallback since some browsers pause a script-unmuted clip that had no *activating* gesture (mousemove/wheel don't grant activation) — `engage()` is idempotent so the imminent click/scroll recovers it. All paths early-out on the `file://`/failed state. **v45 repair**: the muted autostart silently broke — YouTube stopped honouring the old `onReady → mute() → playVideo()` combo (the embed now checks the muted flag when it *loads*; a player created without it just sits UNSTARTED until a real gesture, which read as "music only starts when I touch something"). Fix: `createPlayer` declares `autoplay:1, mute: effMute()?1:0` in `playerVars`, so the mute flag exists at embed birth; the `onReady` volume/mute/play logic is unchanged and still governs every later transition. If muted autostart ever regresses again, suspect another YT embed-policy change and verify over http with a fresh headless-Chrome profile (default autoplay policy) watching for the `#music` bar reaching class `playing` with no input events. **Playlist order is user-editable** (v35): dev tools ▸ "Playlist order…" opens a compact drag-to-reorder modal (`#playlist-modal`, built in the IIFE, list of all 78 tracks with grip/number/label, drop-below-lands-after semantics); the order persists in `localStorage` (`pf_music_order`, array of ids — unknown ids dropped, newly-added tracks appended so it survives playlist growth), applied over the live `TRACKS` in place at startup. `MASTER` snapshots the original curated order for the modal's "Reset order". Reordering keeps `idx` pinned to the now-playing track by id. The Begin journey/Free roam buttons moved down one slot (**v47**: renamed **Enter** / **Roam**, both pinned to the same slot `top:53px` since `syncButtons` only ever shows one at a time; they swap in place) to give the bar the corner. **YouTube refuses ALL embeds on `file://` pages** (error 153, empty referer — verified per-track in headless Chrome, v31): music cannot work when index.html is double-clicked, only when served over http(s). The bar detects this (`location.protocol==='file:'` in `onError`) and labels itself "file:// blocks streaming — use open portfolio.bat"; `open portfolio.bat` (repo root) starts `python -m http.server 8123` minimized and opens `http://localhost:8123/` — the double-click way to browse the site with working music. The deployed/hosted site is unaffected.

## How the scene works

Bounds/derived constants are computed once from the embedded `asciiData` JSON (13,268 `{x,y,z,char}` instances): `centerX/Y`, `spanX/Y`, `midZ`, `farDist`. Glyph grid spacing is `0.6` (x) × `1.0` (y) — used wherever code needs real neighbor/row adjacency.

**The journey** (v20+, replaces the old "descend through the portrait" model): the portrait is treated as terrain (glyph z = relief height). A centripetal Catmull-Rom path snakes over the face through 20 waypoints (10 of them exhibit stops), altitude = local terrain max (`terrainH`, ±5×±3-cell window over `TERRAIN` heightmap) + `JCLEAR` (default 7), passed through a ±9-sample moving max (climb *before* hills) and 3 box-smooth passes, clamped to never dip below the safe height — collision-free by construction (validated numerically against the data). `pathPos(s)` is arc-length parameterized; `poseAt(s)` gazes `LOOK_AHEAD_U` (16 units) down-path with pitch clamped to ~11°–30° so every stop frames the landscape consistently. Content lives in the `JOURNEY` array (marked `EDIT YOUR CONTENT HERE`): per stop `{id,label,title,body,media:[{src,caption}],links:[{href,label}]}`.

**UI state machine** (`uiState`):
- `overview` — free orbit via `OrbitControls`, as before.
- `entering` — flies from the current camera pose to a stop's pose (duration scales with distance).
- `journey` — two sub-modes (`jMode`): `docked` (holding a stop: idle breathing drift, hint visible; in assemble mode free 360° drag-look + facet firing, scroll charges the departure bar; in panel mode the classic damped mouse-look ±~30°/±17° where drag *or* scroll charges departure; 650 ms dock cooldown swallows trackpad inertia) and `flying` (three selectable travel styles — see below). Rail dots and arrow keys also travel; Esc exits to free roam; scrolling past either end gives a soft rebuff bounce.
- `exiting` — **Free roam** button; returns to the overview framing and re-enables OrbitControls.

**Travel styles** (v44; **split into two settings in v47** — dev tools has separate "Travel — Adjacent stops" (`travelAdjacent`, default **cruise**) and "Travel — Far stops" (`travelFar`, default **swoop**) dropdowns. `departTo` picks per hop: neighbouring stops — index diff 1, i.e. scroll/arrow steps — fly `travelAdjacent`; jumps across the path — a rail-dot click more than one stop away — fly `travelFar`. `buildFlight(s0,s1,toIdx,mode)` takes the chosen `mode` explicitly; each departure snapshots its style into the `flight` object, so switching mid-flight is safe). The complaint driving this: classic maps ONE `easeInOut` over the whole arc, so a long trip (welcome→contact ≈ 294 units, capped at 6.5 s) gets sluggish multi-second ramps at both ends and a whipping middle over the snaking spline, with the damped quaternion visibly lagging. The styles: `classic` (the original: eased arc-length flight along the path, `dt*7` damped quaternion follow, `sin` FOV stretch — kept byte-identical in feel); `cruise` (the rail flown properly: a trapezoid velocity profile — `CRUISE_RAMP` 1.0 s sin²-eased acceleration/deceleration around a constant cruise speed `vc = clamp(18+D·0.14, ·, 48)` floored at `D/5.5` so total time caps ~6.5 s; adjacent stops ≈ 2.4–2.8 s, full run 6.5 s at steady 53 u/s; the closed-form integral lands exactly at D with v=0 — validated numerically. Gaze look-ahead grows with speed (`LOOK_AHEAD_U + v·0.55`, via poseAt's optional 4th arg) which irons out spline wiggle, the damped follow tightens with speed, a `chase` quaternion banks into turns from the smoothed yaw rate (cap ±0.26 rad, fades with speed → gone at landing), FOV boost rides actual velocity, and the last-`tA` deceleration blends `levelQuat` for the assemble-mode arrival); and `swoop` (off the rail entirely: rises from the exact current camera pose — no snap — glides a straight-line arc over the portrait and descends into the target; z = lerp + `hump`·sin(π·ek) where `hump` = max(3 + 0.09·horizDist, terrain requirement sampled at ~0.5-unit steps against `terrainH`+`JCLEAR`+0.4) — validated against the real `asciiData`: mid-arc clearance never dips below JCLEAR; duration `1.5 s + 16 ms/unit` capped 3.9 s, so the longest hop is one calm ~3.5 s arc instead of a 6.5 s rail sprint. Heading is constant (straight hop), so the gaze just pitches along the velocity (clamped ~[−41°, +8°]), slerping out of the departure gaze over the first 25% and into the (assemble-leveled) arrival gaze over the last 32% — no damped follow needed, zero lag by construction). All three land through the same `dock()` touchdown-pose blend (v41), so arrivals stay seamless. Only stop-to-stop flights are affected; `entering`/`exiting` are unchanged. **v49** added two further swoop variants to both dropdowns: `swoop2` (curved hop — quadratic-bezier bow in the horizontal plane instead of the straight line, raised-cosine sin² climb, gaze riding the velocity with a milder pitch clamp so it never stares down) and `swoop3` (same curve with a stronger bow, gaze locked on the destination — eye level at the arriving stop — plus a bank into the sweep that fades at both ends); both hump-validated against the terrain like the original swoop. Defaults are unchanged (`cruise`/`swoop`).

**Fullscreen + corner X (v47).** The old top-left `#meta` "ASCII PORTRAIT · 13,268 NODES" label is replaced by `#fs-btn` — a minimalist ASCII-style fullscreen toggle (black fill, thin white border, a bare mono `X`, invert on hover) in the same top-left slot. Browsers refuse `requestFullscreen()` outside a user gesture, so there is no true on-load fullscreen: `fsFirst` (one-shot `pointerdown`/`keydown` listeners) requests it on the visitor's first activating gesture, and clicking the X toggles thereafter (`enterFS`/`toggleFS`, all guarded). The browser's own "press ESC to exit fullscreen" overlay is chrome that page code cannot suppress. **Rail label (v47):** the `.rail-stop.current .lbl { opacity:1 }` rule was removed — the current dot stays lit but its text only shows on hover (per-stop or `#rail:hover`), so leaving a stop to free roam no longer strands its label on screen.

**Stop info display** (v23, reworked v26–v27 — dev tools > "Stop Info" dropdown): `assemble` (default) or `panel` (the classic HTML overlay + clamped mouse-look, kept intact). In assemble mode a docked stop is a panorama of **facets** (text blocks / ASCII covers) hung at fixed yaws around the camera, **all at eye level** (v37 — anchor z = the camera's own z, pitch 0, so content sits where the scene is and the visitor never cranes); the visitor has free 360° drag-look (`freeYaw`/`freePitch`, street-view drag; scroll still departs, so panel-mode's drag-to-depart doesn't exist here). Each facet fires/releases on **yaw alone** (v37 — horizontal slices: fires within `F_GAZE_IN` ~23° of its compass direction, releases past `F_GAZE_OUT` ~35°; pitch never gates, so looking up or down cannot miss or drop content — with 360/7 ≈ 51.4° gallery spacing the ±23° fire windows can't overlap): its recruits fly staggered quadratic-bezier arcs, swap geometry mid-flight (shared `glyphGeo` cache), and settle as world-anchored content; **every other glyph in that facet's sight corridor is absorbed too** (flies into a random letter, fading only as it lands) — so content reads on pure black, and since v43 **nothing merely fades in place** (fade-in-place survives only as a budget-overflow fallback the raised budget makes unreachable). Partitioning happens once per dock (`assembleStop`): items exclusive per facet (nearest to its anchor, reading-order paired); **every** facet whose patch contains a glyph gets its own absorb record for it (v43 — was: corridor leftovers to the angularly nearest facet only) — gaze changes just replay cached flights, no per-frame searches. **The whole corridor joins the assembly (v40)**: pass 3 records EVERY glyph inside a facet's ellipse — other facets' owned letters included — for absorb flights staggered over the same window as the letter flights (budget `F_EXTRA_MAX` 9000 since v43, raised past the measured worst case ~7.2k members per corridor, validated against the real `asciiData`, so overflow never happens in practice). The near-field gate is `v.dot(F.dir)<0.2` (v43; was 1.2 in v41, 4 before) and each glyph's rim widens with proximity (`×(1+(10−vlen)·0.06)` under 10 units). **The sight cone (v43 — replaces scrapped v42's whole-foreground clearing; `v42.html` was deleted, its number stays burned)**: any glyph nearer than the content plane (`depth<dist+2`) and inside the content block's *exact angular footprint* (`coneY/coneP` = block half-extent + 0.06 rad — catches the rectangle's corners, which the inscribed ellipse missed, and glyphs right at the POV) always gets an absorb record, budget-exempt, on every facet type — nothing sits still or fades between the visitor and the text/image/buttons, while the background beyond the content is untouched (v42's mistake was clearing the whole ±60°/±49° facing view). **Facet-to-facet handoff (v43)**: absorb records are self-clocked (`rec.st`/`rec.mode`, animated in every non-`home` state, so a *holding* facet can still receive) and `m.userData.hold` names the facet currently animating a glyph, arbitrating every conflict. Because the gaze hysteresis makes a neighbor fire *before* the current facet releases, `facetOut` looks each departing glyph up in `stopFacets.byMesh` and, if an active facet has a record for it, launches that record (`launchAbsorb`) instead of the home flight — the old facet's letters fly *straight into* the new content instead of returning home and fading (items flag `handed` so their stale home flight can never resume). `facetIn` conversely steals from an `'out'`-state owner/holder mid-flight, and owners always reclaim their own letters (`facetIn` items clear `hold`). Departure (`disassemble`) passes `noHand=true` so everything genuinely flies home. Handed-off letters morph back to home geometry+color mid-flight; the receiver's landing/restore paths fully restore geometry (`rec.g0`), color and `userData.asm`, so a glyph can bounce A→B→A indefinitely. Ordinary stops have one facet dead ahead (auto-assembles on dock; layout via `buildStopLayout`). **v37 removed the whole facet-height machinery** — the per-direction needed-height (terrain clearance), the ~24° elevation cap and the gallery's shared ring height are gone; every anchor is simply eye level, and the elliptical clearing already guarantees legibility over any terrain. **Arrivals are continuous (v40, sealed v41)**: the flight itself blends the down-gaze up to the horizon over its last 30% (`levelQuat` slerp in the flying branch; the entering branch levels its target outright — assemble mode only, panel mode keeps the raw `poseAt` gaze), and `assembleStop` sets `freePitch=freePitchT=-pitch0` so the docked camera math starts exactly where the flight ended. `frame()` also caps dt at 50 ms: the gallery dock's heavy partition used to inflate one frame's dt and make the old arrival ease consume ~90% of its travel in a single step (the v39 "arrival snap"). v41 removed the last residual cut-over: `dock()` captures the exact touchdown pose (`dockT0`/`dockPos`/`dockQuat`) and the docked branch eases from it into its own pose math over 1.6 s (`dr` lerp/slerp) — so the flight's damped-follow lag, the `lookTX/lookTY` mouse sway and the idle breathing drift all fade in instead of switching on at full amplitude at flight end. (A dev-tools re-assemble while already docked sees `dr`=1, i.e. no blend.) The **clearing is elliptical, not rectangular** (v27): each facet fades/absorbs every glyph inside a jittered angular ellipse (`Ry/Rp` = block half-extent + 0.15 rad, per-glyph rim jitter + per-glyph fade rates via `fades[].k`), patches may overlap between facets (v43: every overlapping facet keeps its own absorb record; `userData.hold` decides who animates). Fade speed was retuned in v39 (`F_FADE_MS` 420→260, `k` floor 0.5→0.9) — the slowest glyphs used to linger visibly after the text had assembled. A stop with a `gallery:` array (the **Case studies** stop, waypoint xf-0.34/yf0.22) adds 6 ASCII covers ringing the visitor at **even 360/7 spacing** (earlier ±170° spread put buses/food only 20° apart), all level at eye height like every other facet (v37; the old shared max-zNeed ring is gone). `ASCII_COVERS` (~11KB) is generated **offline** by `gen_covers.py` (34-col grids, ramp `' .:-=+*#%@'`, bright paper covers auto-inverted so ink glows, cells colored by luminance via `setImgColor`). **v36 full-frame fill**: the three white-background covers (`vrchat`, `radiology`, `wegovy`) were regenerated so the *whole* frame is ASCII, not just the subject — earlier they mapped the white paper to spaces (empty), so the cover was subject-shaped and the develop into a rectangular photo looked wrong. The regen (from `images/*.png`, box-downsampled to the same cols×rows, inverted `val=1−L`, ramp index = `1 + round(val·8)` so the floor is `.` never space) fills the background with a faint dotted field while the darker subject still reads as denser/brighter glyphs. Same cols/rows/cw/ch, so layout is unchanged; the other covers (`networks`/`buses`/`food`/`buses_art`, already ~90–99% filled) were left byte-identical. Filling these three raises the gallery from ~5.3k to ~8k of the 13,268 glyphs — still well under the single-partition budget (`assembleStop` pass 2 claims all 7 facets at once from the shared pool). No standalone `gen_covers.py` in the repo; regenerate inline from `images/` if the source covers change. **The develop** (v27): ~0.45s after a cover finishes assembling (`PHOTO_DELAY`), the real front page fades in as an 8-column grid of textured tiles (`buildPhotoTiles`, staggered `PHOTO_STAGGER/TILE_MS`, placed 0.35 behind the glyph plane) while the image glyphs dissolve; the title stays as glyphs; looking away folds the photo up fast and everything scatters home (repeatable). Textures come from `COVER_PHOTOS` — **data-URI JPEGs (512px, ~320KB total, generated offline by `gen_photos.py`)**, because external image files would taint WebGL under file://. The bus cover (`ascii:'buses_art'`) assembles from the pre-made ascii-art variant before developing. Regenerate both embedded blocks after swapping cover images. **Cover layout & buttons (v37, reworked v39–v40)**: each gallery entry carries `tags`/`sub`/`blurb`/`pdf`/`more` alongside `img`/`title`. `buildCoverLayout` stacks (top→bottom): title (**always one line** — long titles auto-shrink from s 0.95 to fit ~23 units instead of wrapping) → subtitle (s 0.55) → the ASCII cover grid → blurb (s 0.55, wrap 48) → the button row. Tags do NOT appear on the cover (v40) — they render as chips in the READ MORE card only. Cover `hFit` is 1.25 (the fit math uses `BASE_FOV` 52 but the docked FOV is 80, so >1 is real headroom; this keeps the developed image at its v38 size, f=1.0 for all six covers). **Glyph budget is TIGHT (v41)**: the 5×7 stencils put the gallery at ~12.6k items + ~300 intro ≈ 12.9k of the 13,268 pool (~400 spare). Adding text to any cover (longer blurb/title/sub) can overflow the pool, which silently shorts the LAST-claimed cover (food) — validate with a quick Python count against `ASCII_COVERS` before shipping content edits. **Buttons are ASCII stencils (v40, refined v41)**: solid blocks of white `'#'` glyphs with the label (DOWNLOAD / READ MORE) punched out as holes, so the black letters are the background showing through — built from `BTN_FONT` (5×7 bitmap caps since v41, only the letters those labels need) on a `BTN_CELL` 0.19 grid, 1-cell padding, glyph scale cell×1.15 (any larger and the fill bleeds into the 1-cell hole strokes and swallows the letters — that killed the first v41 attempt at cell×1.5). Button items are flagged `btn:'pdf'|'more'` and `L:null` (they assemble from glyphs like all text and survive the photo develop); each button records a padded layout-space hit rect in `lay.btns`, which the facet copies (`F.btns`, each `{kind,cx,cy,hw,hh,items,hover}`; items collected in partition pass 2). `updateFacet` pulses settled button glyphs gray→white (`BTN_DIM` #a8a8a8 → `BTN_HOT` #fff, hover pins bright + pointer cursor; skipped when inverted), and the download button does one scale "pop" (`BTN_POP_DELAY` 1.5s after hold, `BTN_POP_MS` 450, ×1.3 sine — reads as a bold flash on the solid block) — scale writes only in 'hold' so flights are never fought. Clicking = a `pointerup` within 6 px of its `pointerdown`; `facetButtonHit` intersects the pointer ray with the facet plane and tests each rect: 'pdf' → `downloadPDF` (v43: `window.open(_blank)` — the report opens in its own tab instead of hijacking the site's tab; the READ MORE card's download link is `target="_blank"` too), 'more' → `showMore(F.g)` opens **the READ MORE card** (`#more-card`, an HTML side panel styled like `#panel`, left-center, z 7) with the project's Context/Methods/Outcomes (per-entry `more:{context,methods,outcomes}`, all English) plus a download link. The card closes on ×, Esc (checked before Esc-to-free-roam), the cover releasing (`facetOut` of any `F.g` facet), or `disassemble`; while open, the window `wheel` handler early-outs so reading can't charge a departure (the card itself stops wheel propagation and scrolls natively). The stop's mini dock keeps the six HTML PDF links as before. Budget: gallery needs ~5.3k of the 13,268 glyphs. `disassemble(true)` instant-restores everything (called from `beginIntro`, `genRun`, `assembleStop`); departure animates facets home via the `asmRetired` list. The HTML panel drops to a `mini` bottom dock with media thumbnails + link buttons (the gallery stop carries all six report PDFs there). Media images and PDFs live in `images/` and `pdfs/` (from the old `portfolio-main` site, which also supplied the stop content). The journey is now **7 stops** (welcome, profile, Orange Wheel, startups, case studies, skills, contact) — the old separate case stops' waypoints remain as plain path points, so the flight path is unchanged.

**Stop markers: none** (removed across v24–v25 at the user's request as wayfinding clutter). The v20 beacon system — numbered text plaques *and* the additive light pillars/beams — plus the breadcrumb path dots are all gone, along with their helpers (`makeSignTexture`, `roundRectPath`, `pickPlaque`/the plaque raycaster, `buildCrumbs`, `buildBeacons`, `syncJourneyPalette`, `BEAM_TEX`) and the "Path dots" dev toggle. **The flight path itself is unchanged** — only the visual overlays came off. Arrival at a stop is announced solely by the assembled text (or the HTML panel); stops are reached via scroll/drag, arrow keys, and the rail list.

**Intro reveal** (the `surface` load animation): on load, all glyphs start at scale 0. A multi-seed flood fill (Game-of-Life-style, 8-neighbor Moore neighborhood over the real sparse grid, randomized branch order + jitter + occasional early "sparks") assigns each glyph a delay, so the portrait spawns into existence organically rather than as a uniform ripple. Runs once, self-terminates. (The default load animation is now `progressive-soft` — see the intro/animation notes above.)

**Journey FOV/bloom automation** (v33, retuned v34): a factor `journeyT` (0 in free roam … 1 at a stop) drives FOV widen `BASE_FOV`→`JOURNEY_FOV` (52→80) and bloom fade-to-0, applied in one place at the end of `frame()`. **v34 fix**: journeyT is no longer an independent exponential smoother — that ran fastest at t=0, so the FOV widened *before* the ease-in camera dolly began moving, which read as a zoom-out-then-in. Instead each state branch sets journeyT from *its own* eased transition progress: entering `journeyFrom+(1-journeyFrom)*ek`, exiting `journeyFrom*(1-ek)`, steady overview/journey pinned to 0/1. So FOV+bloom ride the exact same `easeInOut(k)` curve as the enter/exit camera move — slow at both ends, synchronized. `journeyFrom` (captured in `beginEnter`/`beginExit`) keeps an interrupted/reversed transition continuous. The dev bloom sliders write a separate `baseBloom` object (the overview target); the live pass is `bloom.* = baseBloom.* * (1 - journeyT)`, so sliders and automation never fight — free roam shows the slider values, a docked stop shows zero. **v50 perf**: at strength exactly 0 — i.e. every docked frame and every stop-to-stop flight, since `journeyT===1` pins it there — `bloom.render` is wrapped to short-circuit to the pass's own base blit (the byte-identical first step the full pass runs), skipping the high-pass, ten separable blurs, composite and additive blend (~13 fullscreen GPU passes/frame) whose contribution is mathematically zero (`bloomStrength*(…)=0`, additive `+0`). The pass CHAIN is untouched (scene still renders into the 4× MSAA half-float target and blits through the same material), so blending/tone-mapping spaces are unchanged — do NOT "optimize" further by disabling the pass or dropping `antialias:true`/the composer at strength 0: that reroutes the scene straight to the canvas, where transparent glyphs blend in 8-bit sRGB instead of linear half-float, which is visibly different. Any strength > 0 runs the original full path. The four per-state `camera.fov=…` writes were collapsed into this one (flight's `fovBoost` hoisted). Since journeyT only changes during entering/exiting (states that always render), the overview idle-skip needs no special-casing.

**Dev tools**: gear icon (bottom-left) opens a panel for live-tweaking bloom strength/radius/threshold, FOV, fog near/far, vignette toggle, journey **Path Height** (rebuilds the path live), **Load Animation** and **Stop Info** dropdowns. (Bloom/FOV sliders feed the automation above — see that note.) A **Raw (no processing)** toggle (v19) bypasses every layer added on top of the grainrad export — the whole EffectComposer/bloom path (frame loop falls back to `renderer.render`), ACES tone mapping, fog (`scene.fog=null`; `sceneFog` keeps the tuned object), vignette, and the `#e8ecf3` tint (pure `#ffffff` instead) — reproducing the raw generator scene's look. The composer renders into a 4× multisampled half-float target, because EffectComposer otherwise drops canvas MSAA and visibly aliases glyph edges.

## Conventions from this project's history

- Always validate camera-math/data-dependent changes (distances, fog thresholds, grid spacing, flood-fill reachability) against the real embedded `asciiData` using a quick script before shipping (Node is not installed on this machine; Python 3.11 is available as `python`). JS syntax can be checked with the `esprima` pip package.
- The file CAN be browser-tested from here (since v28/v29): `.claude/launch.json` defines a `portfolio-static` config (`python -m http.server 8123`; `portfolio-static-8124` is a fallback for when another session holds 8123) for the Claude preview tools — navigate to `/vN.html`, check console logs, screenshot, and drive the journey by clicking `#enter-btn`/rail dots and dispatching PointerEvents on the canvas. Caveats: WebGL there is software-rendered and the hidden tab throttles rAF to ~1/s between tool calls, so animation-timing/FPS observations are unreliable — use it for correctness and settled-state visual parity, not performance numbers.
- Still report clearly what to check when the user opens changes in a real browser (real-GPU behavior, animation feel and frame rate can only be judged there).
