# Portfolio 2.0 — ASCII Portrait Site

A single-file, no-build Three.js prototype: an interactive ASCII-art portrait (13,268 glyphs) the visitor can fly through. No framework, no bundler — everything lives in one HTML file.

The portrait data (as of v18) is a direct Grainrad ASCII generator export (172×157 grid, standard charset `.:-=+%#@*`, all-white). The 19 frames in `PROGRESSIVE_FRAMES` (34 → 3,791 glyphs, coarse → fine) drive the "Progressive" load animation; unlike the pre-v18 set (which came from Grainrad itself), they are generated offline by downsampling the embedded `asciiData` onto coarser grids (5 → 64 columns, representative glyph per cell = fine glyph nearest the cell centre, cell z = mean depth) — so a portrait swap requires regenerating them from the new data. Bounds/constants (`centerX/Y`, `spanX/Y`, `midZ`, `farDist`, fog, the journey path and its terrain heightmap) are all derived from the embedded `asciiData`, so swapping the portrait data automatically re-scales the whole scene. Glyph geometry is cached per unique character (`glyphGeo`) and shared across all instances — required at this glyph count — with a dash fallback for symbols the helvetiker font lacks (`∏ ∑ √ ÷ ≠ ≥ ≤ ×`). Since v28 the geometry is a flat `ShapeGeometry` (same font outlines the old extruded TextGeometry used; the 0.02 extrusion was invisible on billboarded unlit glyphs and doubled the triangle count).

**Rendering architecture (v29 — instanced pools).** The 13,268 glyphs are NOT individual meshes anymore (they were through v28, which was the old-hardware bottleneck: 13k draw calls + per-object matrix/cull/sort work every frame). Each unique character owns one `InstancedMesh` (a "pool", 9 for the portrait charset, more created lazily for assembled stop text); a glyph is a lightweight `Glyph` proxy `{position, scale, visible, material:{color,opacity}, geometry, userData}` holding a slot in a pool, so all animation code manipulates proxies exactly like the old Meshes. Assigning `.geometry` (the facets' mid-flight character swap) moves the glyph between pools. `syncPools()` rewrites the instance buffers only on frames where glyph state changed (`glyphsDirty` — every animation path sets it; a missed path shows up as glyphs frozen until the next dirty frame, so set it when adding new animations). **v50**: `syncPools` additionally compares every value before writing (in f32 via `Math.fround` — the proxies hold f64, the arrays f32, so raw compares would never match) and flags `needsUpdate` per attribute per pool only when bytes actually changed — a settled docked stop (where `updateAssembly` marks `glyphsDirty` every frame merely because facets exist) uploads nothing, and e.g. the gallery's button pulse re-sends only the `#` pool's colors instead of all ~1MB of instance data. `glyphsDirty` semantics are unchanged — keep setting it from every animation path; the compare only skips bytes-equal GPU uploads, so it cannot cause the frozen-glyph failure mode. Billboarding is free: instance matrices carry translation+uniform-scale only and the camera quaternion (`BB_UNIFORM`/`uBB`, one shared uniform) rotates glyph vertices in the vertex shader via `GLYPH_MAT.onBeforeCompile` (which also adds the per-instance `instanceOpacity` attribute; per-instance color rides the built-in `instanceColor`). All pools share the single `GLYPH_MAT`; pool geometry is a *clone* of the `glyphGeo` cache entry because the generator preview still uses the cache geometry on plain Meshes. Photo tiles get `renderOrder=-1` (draw before the pools) to preserve the old per-mesh depth-sort behavior during the develop. A `renderDirty` flag forces repaints for non-camera changes (dev sliders, invert/raw, generator); a fully settled overview skips rendering identical frames. Known acceptable deviation: overlapping *semi-transparent* glyphs blend in pool/slot order rather than exact depth order, visible only mid-animation on black — the settled scene is unaffected. The generator preview (`genPreviewMeshes`) still uses plain Meshes.

**Load animations** (selectable in dev tools, replayable): `progressive-soft` (default, v22 — same coarse→fine ramp, but instead of the final hard cut the 13k real glyphs dissolve in individually over ~2.2 s, staggered with a slight peaks-first bias, while the held last frame melts away underneath; the camera push-in spans the whole run so the finish has no jump), `progressive` (the original ramp — resolves through the 19 frames, then snaps to the full portrait; the snap is a ~3.5× density jump, which is why the soft variant exists) and `surface` (the ember/parallax reveal: glyphs surface out of the relief, igniting hot then cooling, while the camera arcs from a close 3/4 angle out to the overview). `beginIntro(mode)` is the single entry point.

**Music bar** (v30; playlist grown to 78 tracks in v32): a minimal fixed pill in the top-right corner (`#music`, styled like the journey buttons — 10px uppercase mono, hairline border, blur backdrop) streaming the playlist through a hidden 2×2 YouTube IFrame player (`#yt-audio-wrap`). It's a self-contained plain `<script>` IIFE just before the main module — playlist lives in its `TRACKS` array (id + "Artist — Title" label; adding a song is genuinely plug-and-play — append one entry, the bar auto-skips any that turn out embed-disabled). New batches are parsed offline from a links markdown and oEmbed-checked for dead/private IDs before insertion. UI: 4-bar CSS equalizer (animates when `.playing`, staggered opacity pulse while `.wait`ing for the stream), marquee title (ping-pong `--mq`/`--mqd`, only when the label overflows 172px; the title is a link to the video on YouTube), prev (restarts after 3 s, classic behavior), play/pause, next, and volume (slider expands on hover; scrolling anywhere on the bar nudges volume and flashes the slider via `.volshow` — `stopPropagation` keeps it from charging the journey departure; window pointer handlers already ignore non-canvas targets). The IFrame API script preloads at startup but the embed is only created when playback first starts, so autoplay-with-sound rides the gesture + `allow="autoplay"` delegation; track end auto-advances, embed-blocked videos are skipped (label "stream unavailable — press play to retry" after a full failed cycle; play resets the streak), and volume persists in `localStorage` (`pf_music_vol`; **default 25%** when unset). **Autostart** (v33, reworked v35, repaired v45): browsers block *audible* autoplay without a user gesture but always allow *muted* autoplay, so v35 begins playback **muted the instant the page loads** (`setTimeout(autostart,0)` — the equalizer runs, the clock ticks) and **unmutes on the visitor's first interaction**. `effMute() = muted || !engaged` gates every mute/unmute (onReady + `applyVolume`); the first-interaction path (`engage()`) flips `engaged` and unmutes+plays. `engage` is armed as one-shot capture listeners on `mousemove`/`pointerdown`/`keydown`/`wheel`/`touchstart` — `mousemove` is included so on this cursor-driven page the music usually goes audible the moment the mouse moves; the discrete gestures are the reliable fallback since some browsers pause a script-unmuted clip that had no *activating* gesture (mousemove/wheel don't grant activation) — `engage()` is idempotent so the imminent click/scroll recovers it. All paths early-out on the `file://`/failed state. **v45 repair**: the muted autostart silently broke — YouTube stopped honouring the old `onReady → mute() → playVideo()` combo (the embed now checks the muted flag when it *loads*; a player created without it just sits UNSTARTED until a real gesture, which read as "music only starts when I touch something"). Fix: `createPlayer` declares `autoplay:1, mute: effMute()?1:0` in `playerVars`, so the mute flag exists at embed birth; the `onReady` volume/mute/play logic is unchanged and still governs every later transition. If muted autostart ever regresses again, suspect another YT embed-policy change and verify over http with a fresh headless-Chrome profile (default autoplay policy) watching for the `#music` bar reaching class `playing` with no input events. **v52 load-yield**: the engage/gesture listeners already attach during initial parse (in the IIFE, before the module's scene build), so first-gesture detection starts the instant the page opens — but the module's ~13,268-glyph build ran *synchronously* inside the FontLoader callback and froze the main thread for its whole duration, during which no queued `mousemove`/gesture and no YouTube `onReady`/gamble callback could fire (music + mouse felt dead "while the scene loads"). The build (and `beginIntro`) is now deferred one macrotask (`setTimeout(…,0)` inside the font callback), so any first gesture made during the font fetch unmutes and the player is created+started *before* the freeze; since YouTube streams from its own iframe process, audio then keeps playing through the build. The deferral is visually free (the font fetch already dominated the wait). If the build is ever made synchronous again, the "music won't start until I move the mouse a second time / after the scene appears" symptom returns. **Playlist order is user-editable** (v35): dev tools ▸ "Playlist order…" opens a compact drag-to-reorder modal (`#playlist-modal`, built in the IIFE, list of all 78 tracks with grip/number/label, drop-below-lands-after semantics); the order persists in `localStorage` (`pf_music_order`, array of ids — unknown ids dropped, newly-added tracks appended so it survives playlist growth), applied over the live `TRACKS` in place at startup. `MASTER` snapshots the original curated order for the modal's "Reset order". Reordering keeps `idx` pinned to the now-playing track by id. The Begin journey/Free roam buttons moved down one slot (**v47**: renamed **Enter** / **Roam**, both pinned to the same slot `top:53px` since `syncButtons` only ever shows one at a time; they swap in place) to give the bar the corner. **YouTube refuses ALL embeds on `file://` pages** (error 153, empty referer — verified per-track in headless Chrome, v31): music cannot work when index.html is double-clicked, only when served over http(s). The bar detects this (`location.protocol==='file:'` in `onError`) and labels itself "file:// blocks streaming — use open portfolio.bat"; `open portfolio.bat` (repo root) starts `python -m http.server 8123` minimized and opens `http://localhost:8123/` — the double-click way to browse the site with working music. The deployed/hosted site is unaffected. **Fade-in blip fix (v59)**: the 3 s fade-in used to restart from volume 0 on EVERY inaudible→audible edge, but the embed keeps playing at the OLD volume until the PLAYING event arrives — so a quick pause/resume (or a fresh start, where `onReady` set full volume before playback) blipped loud for a beat, then dropped to the restarted ramp. Now `fadeP` (the ramp's progress) persists: a pause freezes it, a resume *continues* it, once it reaches 1 later resumes play straight at the set level with no re-fade, a manual volume change pins it to 1, and every other `setVolume` path (`onReady`, `engage`) writes `vol*fadeP` so nothing can outrun the ramp. Net effect: the fade-in happens once — the first time sound reaches the visitor — and pause/resume is level-exact ever after.

**Welcome stop — live GitHub data (v53).** The first stop (`id:'welcome'`, flagged `github:true` in `JOURNEY`) assembles a one-view GitHub panorama out of the terrain instead of the generic title/body: the title **"Hi, I'm Thomas."**, a 1:1 recreation of the contribution calendar, a commit-ticker **banner**, and a small ASCII figure of me (the **mini-me**). It's built by `buildWelcomeLayout()` (returns the same `{items,w,h}` facet-layout shape as `buildStopLayout`/`buildCoverLayout`, so the existing facet machinery assembles/clears/restores it for free) plus calendar hit-test data (`calCells`) and the banner placement. `assembleStop` routes github stops through it (`hFit:1.0`), and everything only exists while docked here — leaving flies every glyph home into the face, so there is no separate model to cull. **Calendar**: `GH_STATS.calendar` (per-day `{date,count,level,weekday}`) laid into GitHub's grid (columns = weeks, rows Sun→Sat), one glyph per day coloured by `contributionLevel` via `CAL_DARK`/`CAL_LIGHT` (invert-aware, passed to `setImgColor` as `L={cal:n}`), month labels along the top and Mon/Wed/Fri labels on the left; hovering a cell raycasts to the facet plane (`welcomeCalTip`) and shows a GitHub-style tooltip (`#cal-tip`, "N contributions on Mon D, YYYY"). **Mini-me / welcome figure (v54)**: two selectable characters, config in `WFIG` (grid + display pitch `cw/ch/s` + optional `wave` descriptor), chosen by `welcomeFigure` (`'scene'` default | `'classic'`, dev panel ▸ "Welcome figure", persisted in `localStorage.pf_welcome_figure`; live-rebuilds if docked). `'scene'` = `MINIME2`, a **26×66 = 1120-glyph seated full-body figure** downsampled offline from a second Grainrad export (Downloads `ascii-scene (7).html`, 12,719 glyphs; scratchpad `gen_minime.py` box-averages luminance, ramp `' .:-=+*#%@'`, rows chosen to preserve on-screen aspect at the display pitch). `'classic'` = the original `MINIME` 30×48 headshot. Both render as gray image cells (`L=0..1`) like a cover, placed left of the calendar stack. **Greeting wave** (scene figure only): its viewer-left hand cluster is flagged in the layout (`wave` cells in `WFIG.scene.wave` box `[c0..c1]×[r0..r1]`), and once the facet settles (`state==='hold'`) `updateWelcomeWave` rotates those glyphs as a rigid cluster about the shoulder pivot (`wavePivot`, layout-space, remapped to the facet plane so angle 0 = each glyph exactly on its settled `to`) — a raise, a ~1 s side-to-side wiggle, a lower, then a few seconds at rest, on a `WAVE_PERIOD` loop. Only the ~35 settled hand glyphs move; `welcome.waveItems` caches them per dock, reset in `releaseWelcome`/`assembleStop`. The classic figure has `wave:null` (static). To swap either figure regenerate its grid from the source export with `gen_minime.py`; the wave box/pivot are grid-coordinate constants in `WFIG` and must be re-checked against the new grid. **Section list (v60)**: a clickable menu of the OTHER five stops (welcome excluded), hung as a column left of the figure — each stop's rail label rendered in `BTN_FONT` stencil bitmaps (v61 removed the plain-text "SECTIONS" header and renumbered the nav waves 0-based) as *positive* letters made of `'#'` glyphs (the inverse of the punched-out buttons; the font gained C T U X for the labels). The labels are ordinary layout items (pass 2/3, absorb, handoff, restore all free) but flagged `nav:k`/`wd`, and they land **invisible** during the facet assembly (extras-style fade in `updateFacet`'s dirIn path — so nothing sits still in the corridor); once the facet settles, `updateWelcomeNav` writes them in banner-style — glyphs re-launched from their terrain homes into the letters, swept L→R per label (`wd`), one wave (`nav` index) at a time: `WNAV_DELAY` after `holdT0`, `WNAV_STEP` apart (dev panel ▸ Welcome Stop ▸ "Section list delay"/"pace", `pf_user_defaults` keys `welNavDelay`/`welNavStep`, read live at wave-launch so slider moves affect pending waves; look-away/back replays the whole sequence — detected by `F.t0` changing, which resets the per-item/per-button `shown`/write flags). Each label registers a `nav` hit rect in `lay.btns` (`data` = its STOPS index): hover pins it bright and **swells it ~1.13× about its own centre** (`b.sc` smoothed; position+scale writes only in `'hold'`, snapping byte-exact to `to`/`s1` when settled — never fights the flights), click = `departTo` that stop; unwritten labels don't hit-test (`b.shown` gate; the header is `noHit`). Nav labels skip the buttons' amber throb (steady 0.78 brightness — five labels pulsing in sync read as noise). The list adds ~11 layout units of width, so factory `WELCOME_SIZE` moved 0.80 → 0.90 (three places: slider HTML, the `ud()` default, `CTRL_DEF`) to keep the pre-existing content within ~9% of its old on-screen size; welcome's clearing ellipse stays smaller than the validated case-studies worst case, and the stop's glyph total (~2.4k) is nowhere near the pool. **Commit banner (the horizontal waterfall)**: NOT layout items — `reserveWelcomeBanner` claims ~30 terrain glyphs near the banner line BEFORE the facet partition (marked `owner=100` so pass 2 skips them; pass 3 skips reserved so they're never absorbed), and `updateWelcome`/`updateWelcomeBanner` animate them (v61: as a per-column stencil STREAM — each cell assembles, lingers, and dissolves on its own column clock, so a stat's head is dissolving while its tail arrives; see the v61 paragraph), advancing today → this month → this year → total. Idle banner glyphs sit invisible at home; `releaseWelcome` (called from `disassemble`) restores them fully so the face is intact on departure. **Stats data** comes from `data/stats.json`, written **ahead of time** by a GitHub Actions workflow (`scripts/fetch-stats.js` + `.github/workflows/stats.yml`) — the browser never calls the GitHub API or sees a token. `loadStats()` fetches it cache-busted (`cache:'no-store'`, `?t=`), polls every 60 s, and on localhost/`file://` with no real file falls back to `data/stats.sample.json` (obviously fake, for local preview); when fresh stats arrive while docked at welcome it re-`assembleStop`s. Everything degrades gracefully when the JSON is missing (placeholder empty calendar, "LOADING COMMITS" banner). All numbers are **public activity only** (the `read:user` token cannot see private repos) and bucketed in **Europe/Copenhagen**. See `README.md` for token rotation / troubleshooting.

## Files

- `index.html` — the single source of truth. This is the only working copy; edit it directly and open it in a browser to preview. Versioning is handled by `git`, not by numbered files.
- `scripts/fetch-stats.js` — Node 20 (native `fetch`) script the Actions workflow runs to write `data/stats.json`. Token from `process.env.GH_TOKEN` only, never logged/committed; exits non-zero without writing on any API failure (never publishes partial/zero data over good data).
- `.github/workflows/stats.yml` — runs the fetch every 30 min + on demand, commits `data/stats.json` as `github-actions[bot]` only when it changed (`chore: update stats [skip ci]`). Needs the `STATS_TOKEN` repo secret (`read:user` scope). **Never attribute these or any build commit to an AI tool** (user requirement — no `Co-Authored-By`, no "Generated with" lines on anything touching this feature).
- `data/stats.sample.json` — fake but structurally identical stats for local preview; the deployed site never uses it.
- `FACET-ASSEMBLY-MANUAL.md` (repo root) — **read this before touching the assembled-stop/facet system** (adding galleries or buttons to other stops, changing clearing/absorb behavior, debugging glyph transitions). Written after v43: architecture, the hold/handoff/cone design, the validation methodology (Python vs. real `asciiData`, esprima), and the pitfalls that already bit us once.

## Versioning (git — no more numbered files)

- **Do NOT create `vN.html` copies.** The old `v1.html … vN.html` snapshot convention is retired; git history is the version record now. Older numbered snapshots are archived in `../Portfolio older versions/`.
- **After each round of changes, commit.** One commit per change round, with a short message describing what changed (the old `vN:` messages are a fine style, e.g. `git commit -am "seamless docking + finer stencil buttons"`).
- **To go back to an old version:** `git log --oneline` to find it, then `git show <hash>:index.html > preview.html` to inspect it, or `git checkout <hash> -- index.html` to restore it.
- **Multiple changes at once:** to work on two things in parallel without them clobbering each other, use a separate branch (or git worktree) per task, then merge each back into `main`. Two edits to the *same* part of `index.html` will still need a manual merge — those are best done one at a time.

## How the scene works

Bounds/derived constants are computed once from the embedded `asciiData` JSON (13,268 `{x,y,z,char}` instances): `centerX/Y`, `spanX/Y`, `midZ`, `farDist`. Glyph grid spacing is `0.6` (x) × `1.0` (y) — used wherever code needs real neighbor/row adjacency.

**The journey** (v20+, replaces the old "descend through the portrait" model): the portrait is treated as terrain (glyph z = relief height). A centripetal Catmull-Rom path snakes over the face through 20 waypoints (6 of them exhibit stops since v57), altitude = local terrain max (`terrainH`, ±5×±3-cell window over `TERRAIN` heightmap) + `JCLEAR` (default 7), passed through a ±9-sample moving max (climb *before* hills) and 3 box-smooth passes, clamped to never dip below the safe height — collision-free by construction (validated numerically against the data). `pathPos(s)` is arc-length parameterized; `poseAt(s)` gazes `LOOK_AHEAD_U` (16 units) down-path with pitch clamped to ~11°–30° so every stop frames the landscape consistently. Content lives in the `JOURNEY` array (marked `EDIT YOUR CONTENT HERE`): per stop `{id,label,title,body,media:[{src,caption}],links:[{href,label}]}`.

**UI state machine** (`uiState`):
- `overview` — free orbit via `OrbitControls`, as before.
- `entering` — flies from the current camera pose to a stop's pose (duration scales with distance).
- `journey` — two sub-modes (`jMode`): `docked` (holding a stop: idle breathing drift, hint visible; in assemble mode free 360° drag-look + facet firing, scroll charges the departure bar; in panel mode the classic damped mouse-look ±~30°/±17° where drag *or* scroll charges departure; 650 ms dock cooldown swallows trackpad inertia) and `flying` (three selectable travel styles — see below). Rail dots and arrow keys also travel; Esc exits to free roam; scrolling past either end gives a soft rebuff bounce.
- `exiting` — **Free roam** button; returns to the overview framing and re-enables OrbitControls.

**Travel styles** (v44; **split into two settings in v47** — dev tools has separate "Travel — Adjacent stops" (`travelAdjacent`, default **cruise**) and "Travel — Far stops" (`travelFar`, default **swoop**) dropdowns. `departTo` picks per hop: neighbouring stops — index diff 1, i.e. scroll/arrow steps — fly `travelAdjacent`; jumps across the path — a rail-dot click more than one stop away — fly `travelFar`. `buildFlight(s0,s1,toIdx,mode)` takes the chosen `mode` explicitly; each departure snapshots its style into the `flight` object, so switching mid-flight is safe). The complaint driving this: classic maps ONE `easeInOut` over the whole arc, so a long trip (welcome→contact ≈ 294 units, capped at 6.5 s) gets sluggish multi-second ramps at both ends and a whipping middle over the snaking spline, with the damped quaternion visibly lagging. The styles: `classic` (the original: eased arc-length flight along the path, `dt*7` damped quaternion follow, `sin` FOV stretch — kept byte-identical in feel); `cruise` (the rail flown properly: a trapezoid velocity profile — `CRUISE_RAMP` 1.0 s sin²-eased acceleration/deceleration around a constant cruise speed `vc = clamp(18+D·0.14, ·, 48)` floored at `D/5.5` so total time caps ~6.5 s; adjacent stops ≈ 2.4–2.8 s, full run 6.5 s at steady 53 u/s; the closed-form integral lands exactly at D with v=0 — validated numerically. Gaze look-ahead grows with speed (`LOOK_AHEAD_U + v·0.55`, via poseAt's optional 4th arg) which irons out spline wiggle, the damped follow tightens with speed, a `chase` quaternion banks into turns from the smoothed yaw rate (cap ±0.26 rad, fades with speed → gone at landing), FOV boost rides actual velocity, and the last-`tA` deceleration blends `levelQuat` for the assemble-mode arrival); and `swoop` (off the rail entirely: rises from the exact current camera pose — no snap — glides a straight-line arc over the portrait and descends into the target; z = lerp + `hump`·sin(π·ek) where `hump` = max(3 + 0.09·horizDist, terrain requirement sampled at ~0.5-unit steps against `terrainH`+`JCLEAR`+0.4) — validated against the real `asciiData`: mid-arc clearance never dips below JCLEAR; duration `1.5 s + 16 ms/unit` capped 3.9 s, so the longest hop is one calm ~3.5 s arc instead of a 6.5 s rail sprint. Heading is constant (straight hop), so the gaze just pitches along the velocity (clamped ~[−41°, +8°]), slerping out of the departure gaze over the first 25% and into the (assemble-leveled) arrival gaze over the last 32% — no damped follow needed, zero lag by construction). All three land through the same `dock()` touchdown-pose blend (v41), so arrivals stay seamless. Only stop-to-stop flights are affected; `entering`/`exiting` are unchanged. **v49** added two further swoop variants to both dropdowns: `swoop2` (curved hop — quadratic-bezier bow in the horizontal plane instead of the straight line, raised-cosine sin² climb, gaze riding the velocity with a milder pitch clamp so it never stares down) and `swoop3` (same curve with a stronger bow, gaze locked on the destination — eye level at the arriving stop — plus a bank into the sweep that fades at both ends); both hump-validated against the terrain like the original swoop. Defaults are unchanged (`cruise`/`swoop`).

**Fullscreen + corner X (v47; made opt-in v52).** The old top-left `#meta` "ASCII PORTRAIT · 13,268 NODES" label is replaced by `#fs-btn` — a minimalist ASCII-style fullscreen toggle (black fill, thin white border, a bare mono `X`, invert on hover) in the same top-left slot. Browsers refuse `requestFullscreen()` outside a user gesture, so there is no true on-load fullscreen: `fsFirst` (one-shot `pointerdown`/`keydown`/`touchend` listeners) requests it on the visitor's first activating gesture, and clicking the X toggles thereafter (`enterFS`/`toggleFS`, all guarded). The browser's own "press ESC to exit fullscreen" overlay is chrome that page code cannot suppress. **v52: auto-fullscreen is now OPT-IN and OFF by default** — dev tools ▸ "Fullscreen on enter" checkbox, persisted in `localStorage.pf_fullscreen`. `fsEnabled` gates `fsFirst`; when off the corner X is hidden (`#fs-btn` ships `style="display:none"` and `applyFullscreenPref` sets its visibility from the saved pref). Toggling the checkbox is itself an activating gesture, so `applyFullscreenPref(on,true)` enters/exits fullscreen immediately; "Reset defaults" turns it back off. **Rail label (v47):** the `.rail-stop.current .lbl { opacity:1 }` rule was removed — the current dot stays lit but its text only shows on hover (per-stop or `#rail:hover`), so leaving a stop to free roam no longer strands its label on screen.

**Stop info display** (v23, reworked v26–v27 — dev tools > "Stop Info" dropdown): `assemble` (default) or `panel` (the classic HTML overlay + clamped mouse-look, kept intact). In assemble mode a docked stop is a panorama of **facets** (text blocks / ASCII covers) hung at fixed yaws around the camera, **all at eye level** (v37 — anchor z = the camera's own z, pitch 0, so content sits where the scene is and the visitor never cranes); the visitor has free 360° drag-look (`freeYaw`/`freePitch`, street-view drag; scroll still departs, so panel-mode's drag-to-depart doesn't exist here). Each facet fires/releases on **yaw alone** (v37 — horizontal slices: fires within `F_GAZE_IN` ~23° of its compass direction, releases past `F_GAZE_OUT` ~35°; pitch never gates, so looking up or down cannot miss or drop content — with 360/7 ≈ 51.4° gallery spacing the ±23° fire windows can't overlap): its recruits fly staggered quadratic-bezier arcs, swap geometry mid-flight (shared `glyphGeo` cache), and settle as world-anchored content; **every other glyph in that facet's sight corridor is absorbed too** (flies into a random letter, fading only as it lands) — so content reads on pure black, and since v43 **nothing merely fades in place** (fade-in-place survives only as a budget-overflow fallback the raised budget makes unreachable). Partitioning happens once per dock (`assembleStop`): items exclusive per facet (nearest to its anchor, reading-order paired); **every** facet whose patch contains a glyph gets its own absorb record for it (v43 — was: corridor leftovers to the angularly nearest facet only) — gaze changes just replay cached flights, no per-frame searches. **The whole corridor joins the assembly (v40)**: pass 3 records EVERY glyph inside a facet's ellipse — other facets' owned letters included — for absorb flights staggered over the same window as the letter flights (budget `F_EXTRA_MAX` 9000 since v43, raised past the measured worst case ~7.2k members per corridor, validated against the real `asciiData`, so overflow never happens in practice). The near-field gate is `v.dot(F.dir)<0.2` (v43; was 1.2 in v41, 4 before) and each glyph's rim widens with proximity (`×(1+(10−vlen)·0.06)` under 10 units). **The sight cone (v43 — replaces scrapped v42's whole-foreground clearing; `v42.html` was deleted, its number stays burned)**: any glyph nearer than the content plane (`depth<dist+2`) and inside the content block's *exact angular footprint* (`coneY/coneP` = block half-extent + 0.06 rad — catches the rectangle's corners, which the inscribed ellipse missed, and glyphs right at the POV) always gets an absorb record, budget-exempt, on every facet type — nothing sits still or fades between the visitor and the text/image/buttons, while the background beyond the content is untouched (v42's mistake was clearing the whole ±60°/±49° facing view). **Facet-to-facet handoff (v43)**: absorb records are self-clocked (`rec.st`/`rec.mode`, animated in every non-`home` state, so a *holding* facet can still receive) and `m.userData.hold` names the facet currently animating a glyph, arbitrating every conflict. **Journey FOV/bloom automation** (v33, retuned v34): a factor `journeyT` (0 in free roam … 1 at a stop) drives FOV widen `BASE_FOV`→`JOURNEY_FOV` (52→80) and bloom fade-to-0, applied in one place at the end of `frame()`. **v34 fix**: journeyT is no longer an independent exponential smoother — that ran fastest at t=0, so the FOV widened *before* the ease-in camera dolly began moving, which read as a zoom-out-then-in. ## Conventions from this project's history

- Always validate camera-math/data-dependent changes (distances, fog thresholds, grid spacing, flood-fill reachability) against the real embedded `asciiData` using a quick script before shipping (Node is not installed on this machine; Python 3.11 is available as `python`). JS syntax can be checked with the `esprima` pip package.
- The file CAN be browser-tested from here (since v28/v29): `.claude/launch.json` defines a `portfolio-static` config (`python -m http.server 8123`; `portfolio-static-8124` is a fallback for when another session holds 8123) for the Claude preview tools — navigate to `/vN.html`, check console logs, screenshot, and drive the journey by clicking `#enter-btn`/rail dots and dispatching PointerEvents on the canvas. Caveats: WebGL there is software-rendered and the hidden tab throttles rAF to ~1/s between tool calls, so animation-timing/FPS observations are unreliable — use it for correctness and settled-state visual parity, not performance numbers.
- Still report clearly what to check when the user opens changes in a real browser (real-GPU behavior, animation feel and frame rate can only be judged there).
